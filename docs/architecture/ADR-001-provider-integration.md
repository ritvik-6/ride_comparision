# ADR-001 — Provider integration architecture for fare comparison

- **Status:** Accepted (Stages 1–4 implemented; no live provider is integrated)
- **Date:** 2026-11-20
- **Scope:** `backend/` — the fare comparison service
- **Supersedes:** nothing

## 1. Context and problem statement

RideCompare shows a rider one comparison across Rapido, Uber and Ola for Bike, Auto
and Cab tiers. The single `POST /api/v1/fares/compare` endpoint that serves this
today returns **deterministic sample data** ported from the mobile app. Those
numbers are honest only because the response says so: `source: "demo"` plus a
disclosure notice.

The next step is authorised provider quoting. That brings four problems the demo
implementation cannot express:

1. **Provenance.** A sample fare and a real quote must never be ranked against
   each other. A "CHEAPEST" badge comparing ₹45 of demo data with ₹180 of real
   data is a lie with a number attached.
2. **Partial failure.** Three network calls can fail independently. One slow
   provider must not delay or remove the other two, and a total outage must not
   produce a price.
3. **Heterogeneity.** Providers differ in ride tiers, whether they need
   coordinates, whether a quote expires, and how a "we don't serve this" answer
   looks. Those differences are facts about each provider, not about the
   comparison.
4. **Credentials.** Authorised access needs secrets. Secrets must not reach a
   response body, a log line, or a client, and a half-configured provider must
   fail visibly rather than silently serving something else.

A decision was needed before any provider code was written, because the shape of
the seam determines whether adding a provider is a new file or a rewrite of the
endpoint.

**Decision:** introduce a provider adapter contract plus an aggregator, with a
domain model layer that is independent of FastAPI and of the wire schema, and make
demo data the first adapter behind that contract. Live integrations are added one
adapter at a time; the endpoint, response schema and app do not change to admit
one.

## 2. Existing demo fare architecture

`app/services/fares/demo_fares.py` is the whole of the pricing logic, and it is
still the only logic that produces numbers.

- `DEMO_OFFERS` is a fixed nine-row table: three providers × three tiers, with
  `base_fare`, `base_eta_minutes` and `available`. Rapido Cab is the intentionally
  unavailable row.
- `stable_hash(pickup_id, destination_id)` is FNV-1a, deliberately reproducing two
  JavaScript behaviours: **UTF-16 code units** for string iteration (so astral
  characters hash as surrogate pairs, as `charCodeAt` does), and **signed 32-bit
  wraparound** on `^=`/`Math.imul` with `>>> 0` for the unsigned result.
- `get_demo_fare_comparison(pickup_id, destination_id)` derives a per-route
  offset from that hash and adds it to each row's base values. Rounding is
  `floor(x + 0.5)` because JavaScript's `Math.round` rounds halves towards `+∞`
  while Python's `round()` is half-to-even.
- Consequences: identical ids always give identical estimates; different ids
  generally differ; coordinates are inert (nothing measures distance); and costs
  are whole rupees with integer ETAs.
- `backend/tests/fixtures/demo_fares_parity.json` is generated by **executing**
  the app's TypeScript module (`tests/fixtures/generate_demo_fares_parity.mjs`),
  not by transcribing it. The suite asserts the Python port matches it, which is
  what stops the two implementations drifting.

The demo decision is load-bearing for the rest of this document: because the
generator is pure, deterministic and I/O-free, it can be wrapped as an adapter and
the resulting endpoint can be proven byte-for-byte identical to the previous one.

## 3. Provider adapter pattern and protocol

```python
class FareProviderAdapter(Protocol):
    name: str
    source: QuoteSource
    providers: tuple[ProviderId, ...]
    capabilities: ProviderCapabilities

    async def compare(self, request: QuoteRequest) -> Sequence[ProviderQuote]: ...
```

`app/services/fares/providers/base.py` defines it structurally (`typing.Protocol`),
so an adapter is a plain class — no inheritance, and test fakes need no base class.

Contract rules, all stated in the module docstring:

- Return quotes only for the requested categories and only for tiers the provider
  actually describes. Never invent a tier name or a price.
- Report "this provider does not serve this tier here" as a
  `QuoteStatus.UNSUPPORTED` quote, **not** as an exception.
- Don't mutate the request or keep mutable state between calls.
- Keep FastAPI, HTTP status codes and wire field names out of the adapter.
- Never put credentials, provider response bodies or raw exception messages into
  an exception the caller can see.

`compare` is `async` because authorised providers are network calls. The one
defined exception is `ProviderNotConfiguredError`, raised when an integration
exists but cannot quote — the deliberate alternative to returning a plausible
number for a provider that isn't wired up.

Four adapters exist:

| Adapter | `source` | `providers` | Behaviour |
| --- | --- | --- | --- |
| `DemoAdapter` | `demo` | all three | Wraps `get_demo_fare_comparison`; maps `available=False` → `UNSUPPORTED`. No I/O. |
| `RapidoAdapter` | `provider-api` | `rapido` | Raises `ProviderNotConfiguredError`. |
| `UberAdapter` | `provider-api` | `uber` | Raises `ProviderNotConfiguredError`. |
| `OlaAdapter` | `provider-api` | `ola` | Raises `ProviderNotConfiguredError`. |

The aggregator enforces one invariant at construction: an adapter's
`capabilities.providers` must equal its `providers`. Two declarations of the same
fact drift; the mismatch is rejected rather than producing states for providers
the adapter cannot name.

## 4. Domain models and quote lifecycle

`app/services/fares/models.py` imports no FastAPI or Pydantic types. That is what
lets adapters and the aggregator be unit-tested without an app, and lets the route
own the entire wire vocabulary.

| Type | Role |
| --- | --- |
| `ProviderId` | `rapido`, `uber`, `ola` — transport-safe `str` enum. |
| `RideCategory` | `bike`, `auto`, `cab`. |
| `QuoteSource` | `demo`, `provider-api`. |
| `QuoteStatus` | `quoted`, `unsupported`, `not_configured` — per quote. |
| `ProviderStatus` | `success`, `not_configured`, `timed_out`, `failed`, `unsupported` — per provider. |
| `ProviderErrorCode` | `timeout`, `total_budget_exceeded`, `provider_error`, `missing_coordinates`. |
| `PROVIDER_ORDER`, `CATEGORY_ORDER` | Response ordering constants. |
| `GeoPoint`, `PlaceRef`, `QuoteRequest` | Normalised request. Only place ids reach the demo generator. |
| `ProviderQuote` | One provider/tier offer. |
| `ProviderState` | How one provider went: status, locally measured latency, optional code. |
| `FareComparison` | Quotes plus states plus `source`. |

Two invariants are enforced in `__post_init__`, because they are the difference
between a clear answer and a misleading one:

- `ProviderQuote.available` is `True` **exactly when** `status is QUOTED`. A quote
  cannot claim to be bookable while reporting its tier unsupported.
- A `ProviderState` cannot carry an `error_code` when its status is `success`, and
  `latency_ms` cannot be negative.

Lifecycle of one request:

```
places  ──►  QuoteRequest  ──►  aggregator.compare
                                  ├─ plan(adapter, request)      ← capabilities
                                  ├─ adapter.compare(...)        ← per-provider timeout
                                  └─ normalise → ProviderCallResult
                                        ├─ ProviderQuote[]  → ordered quotes
                                        └─ ProviderState    → ordered states
                                             ──►  FareComparison  ──►  wire model
```

`QuoteStatus` and `ProviderStatus` are intentionally separate: a provider can
succeed and still report a tier as unsupported (that is exactly what the demo
table does for Rapido Cab), and a provider can fail without producing any quote at
all.

## 5. Provider registry and configuration

`app/services/fares/registry.py` is the only module that reads `PROVIDER_MODE` and
decides what runs. Each provider is a `ProviderSpec` (`provider`, `label`,
`build`, `is_enabled`, `missing_credentials`) in `PROVIDER_SPECS`, ordered as the
response orders providers.

`build_adapters(settings)` returns:

- **`demo` (default):** `(DemoAdapter(),)`. Provider flags and credentials are
  ignored entirely, so a leftover key in a developer's `.env` cannot make a demo
  deployment call anyone.
- **`live`:** one adapter per enabled provider, after two strict checks. No
  provider enabled → `ProviderRegistryConfigurationError`. An enabled provider
  missing a credential → the same error, naming the provider and the *variable
  names*. Raising at startup (via `create_app`) means a broken deployment fails
  before it can serve a request.

A blank credential counts as absent (`SecretStr` value stripped), so a copied
`.env.example` placeholder is not a credential.

Wiring: `create_app(settings)` resolves settings once, validates live mode, and
registers `dependency_overrides[get_settings]` so the resolved settings are
authoritative for every dependency — not just for startup. `api/dependencies.py`
builds `FareAggregator(adapters=build_adapters(settings), request_timeout_seconds=…,
total_budget_seconds=…)` per request; the aggregator is stateless, so this is
plumbing rather than cost. The route depends on `get_fare_aggregator`, which is
how tests inject fakes without touching handler code.

`Settings` (`app/core/config.py`) is `pydantic-settings`, reading `backend/.env`
with real environment variables winning over the file; every value has a
local-development default so the app boots with no `.env`.

## 6. Provider capabilities and unknown/unverified values

`ProviderCapabilities` answers five questions, each as **verified fact or
`None`** (unverified):

```python
providers: tuple[ProviderId, ...]
categories: frozenset[RideCategory] | None
credentials_required: bool | None
coordinates_required: bool | None
expiry_supported: bool | None
```

The tri-state is the core of the decision. A boolean would force a claim, and both
possible defaults are dangerous: `False` for `coordinates_required` invites a call
that cannot be made, `True` blocks a call that could have worked. `None` makes
"we have not verified this" a representable, testable value.

`categories` carries a second distinction: an **empty set** is "verified to serve
no tier here"; `None` is "we do not know yet". `known` and
`supports(category) -> bool | None` expose the difference at every call site.

Declarations in this build:

| Adapter | categories | credentials_required | coordinates_required | expiry_supported |
| --- | --- | --- | --- | --- |
| demo | all three (verified) | `False` | `False` | `False` |
| rapido | `None` | `True` | `None` | `None` |
| uber | `None` | `True` | `None` | `None` |
| ola | `None` | `True` | `None` | `None` |

`credentials_required=True` for the skeletons is the one thing actually known:
it is why the registry demands a key pair. Tier list, coordinate requirement and
expiry stay unknown — nothing in this repository verifies them, and guessing from
what a consumer app appears to offer is not verification.

Demo's capabilities are verified facts about the code in this repository, not
claims about providers: the table really does cover every tier, really needs no
credentials, really works without coordinates, and really has no notion of
expiry.

The aggregator uses capabilities only to *avoid* bad calls — never to assume a
capability exists (see §7).

## 7. Aggregator concurrency and timeout strategy

`app/services/fares/aggregator.py`:

1. **Plan** each adapter before anything is called.
2. Create one `asyncio.Task` per adapter that will be called.
3. `asyncio.wait(tasks, timeout=total_budget)`.
4. Each task internally wraps its adapter in `asyncio.timeout(request_timeout)`.
5. Cancel anything still pending, record it as `timed_out` /
   `total_budget_exceeded`, then `gather(..., return_exceptions=True)` so cancelled
   coroutines unwind before the response is built.

Both limits are configurable: `PROVIDER_REQUEST_TIMEOUT_SECONDS` (default 4.0) and
`PROVIDER_TOTAL_BUDGET_SECONDS` (default 6.0). `Settings` rejects a total budget
below one request timeout — that combination would clip every provider at the same
instant, which reads to a rider as "no rides" rather than "slow".

Planning rules:

- **Known categories** → the request is narrowed to the intersection with the
  declared set, so an adapter is only asked for tiers it claims.
- **Empty intersection** → the adapter is not called; state is `unsupported`,
  latency `0`.
- **`coordinates_required is True` and either end lacks a position** → not called;
  `unsupported` with `missing_coordinates`.
- **`None` anywhere** → no narrowing, no skipping. Absence of evidence is not a
  reason to drop a provider.

Concurrency is why a failing provider cannot slow a working one, and the total
budget is why a hung provider cannot hold the response. Measured order is
discarded: results and states are re-sorted into `PROVIDER_ORDER`, then
`CATEGORY_ORDER`, with a stable sort so ties keep adapter order. Provider states
are emitted per **provider**, not per adapter — the demo adapter covers three
providers and must produce three states when it is used in a live-shaped response.

`asyncio.CancelledError` from a client disconnect cancels the child tasks and
re-raises; no provider call continues behind a dead request.

## 8. Provider failure isolation and `providerStates`

Every adapter outcome becomes exactly one `ProviderState`; nothing propagates out
of `compare()` except cancellation.

| Cause | `status` | `errorCode` |
| --- | --- | --- |
| Adapter returned | `success` | `null` |
| `ProviderNotConfiguredError` | `not_configured` | `null` |
| Per-provider `TimeoutError` | `timed_out` | `timeout` |
| Any other exception | `failed` | `provider_error` |
| Total budget expired first | `timed_out` | `total_budget_exceeded` |
| Skipped by capabilities | `unsupported` | `null` or `missing_coordinates` |

`unsupported` is not a failure: it records that the provider was never asked
because its declared capabilities could not answer this request. Without it the
only way to say "not asked" would be `success` with zero quotes, which a client
reads as "no rides available".

`latency_ms` is measured locally with `perf_counter`, so it reveals nothing a
provider sent. It is `0` for skipped adapters.

Wire exposure: `providerStates` is **live-only**. The demo payload is a published
contract, so the route excludes the key rather than serialising `null` or `[]`
(`model_dump(..., exclude={"provider_states"})` in demo mode). Demo responses stay
byte-for-byte identical to the pre-adapter endpoint; live responses carry the
states. The field is additive, and the mobile app ignores it today.

Failure isolation is also a pricing rule: **there is no fallback to demo data**.
A provider that fails contributes no estimate. If every provider fails, the
response is an honest empty list with `source: "provider-api"` and
`LIVE_NO_QUOTES_NOTICE`.

## 9. Demo vs `provider-api` source separation

- `QuoteSource` travels on every adapter, and `FareAggregator._shared_source()`
  requires all adapters to agree. A mix raises `MixedQuoteSourcesError` at
  comparison time instead of producing a sorted list of half-sample,
  half-real prices. Per-quote provenance does not exist yet; until it does,
  blending is refused.
- The registry never builds a mixed set: demo mode yields only `DemoAdapter`, live
  mode only provider adapters.
- The wire schema accepts `source: "demo" | "provider-api"`, so nothing can serve
  an unmodelled provenance.
- Wording follows the source (`app/services/fares/notices.py`): demo comparisons
  keep `DEMO_ESTIMATES_NOTICE`; live comparisons use `LIVE_ESTIMATES_NOTICE`, or
  `LIVE_NO_QUOTES_NOTICE` when nothing was quoted. No branch can describe sample
  numbers as live.
- The demo generator's values were not adjusted to fit the seam. `DemoAdapter`
  only maps `available=False` to `UNSUPPORTED`; fares, ETAs, tier labels and order
  are untouched, and the parity fixture is unchanged.

## 10. Credential security and environment configuration

- Credentials are `SecretStr`: a `repr`, log line or dump shows `**********`. They
  are readable only via `get_secret_value()`.
- `backend/.env` is gitignored; `backend/.env.example` holds empty placeholders and
  the variable names. Nothing else in the repository contains a credential.
- Blank/whitespace values count as absent, so placeholders never read as keys.
- Registry errors name **variables**, never values — e.g. `Uber
  (UBER_CLIENT_ID, UBER_CLIENT_SECRET)`.
- No credential currently leaves the settings object: all three live adapters
  raise before touching one. `credentials_required` documents the dependency the
  registry already enforces.
- `CORS_ORIGINS` is an explicit allow-list; `*` is rejected at startup, as is an
  entry without scheme and host. This is browser-facing only — the Android app is
  not subject to CORS.

Environment variables implemented today: `APP_NAME`, `APP_VERSION`,
`ENVIRONMENT`, `CORS_ORIGINS`, `PROVIDER_MODE`,
`PROVIDER_REQUEST_TIMEOUT_SECONDS`, `PROVIDER_TOTAL_BUDGET_SECONDS`, and
`{UBER,OLA,RAPIDO}_ENABLED` / `_CLIENT_ID` / `_CLIENT_SECRET`.

## 11. Error handling and safe logging considerations

Implemented:

- The only failure detail that reaches a client is an enumerated
  `ProviderErrorCode`. Exception messages, provider bodies and credentials are
  discarded in `_call`.
- Malformed input is a FastAPI `422` with the standard `detail` array; a provider
  problem is never a 5xx. The endpoint returns `200` with `providerStates` even
  when every provider failed.
- `create_app` validates live configuration at startup, so misconfiguration is a
  boot failure rather than a per-request surprise. (`build_fare_aggregator` still
  raises if live mode reaches it unvalidated, which surfaces as a 500 — a bug
  path, not a supported state.)
- Cancellation is propagated and children are cleaned up.

**Not implemented, deliberately:** there is no logging, no structured logging, no
metrics and no tracing in this service today. Adapter exceptions are swallowed
without being recorded anywhere, which is the correct *data* choice (a body or
token may be inside the message) but leaves no operational trail.

The consequence to accept: when a provider fails in production nobody can tell
which one, how often, or why beyond the client-visible code. The rule for the
phase that adds observability: log `provider`, `status`, `error_code` and
`latency_ms` — never the exception string, never a request body, never a header.
Structured logging must be added as a reviewed change with that redaction rule
built in, not bolted onto the existing `except` clauses.

## 12. Why scraping private APIs and inventing endpoints are prohibited

Applies to provider quoting; the app's deep links are a separate, user-initiated
handoff (§13 context) and quote nothing.

1. **It is unauthorised.** Provider APIs are governed by terms that require a
   partner agreement. Reading a private endpoint, replaying an app's token or
   bypassing auth is access the provider did not grant, regardless of who ends up
   seeing the price.
2. **It cannot be maintained.** Undocumented endpoints change without notice. The
   failure mode is not an error; it is a plausible wrong number, which is worse
   than an outage for a product whose only job is price accuracy.
3. **It corrupts the model.** Capabilities exist to keep unknowns unknown. Scraped
   endpoints would be marked "supported" on the strength of a reverse-engineered
   shape, so `unsupported` would start meaning "our scraper broke", which is
   exactly the failure-versus-capability confusion §8 forbids.
4. **It leaks into the contract.** Fake endpoints or placeholder credentials become
   `PROVIDER_SPECS` entries and test fixtures that look real, and a later reader
   cannot distinguish a verified integration from a guess.
5. **It cannot be tested honestly.** Fixtures recorded from a private endpoint
   encode assumptions nobody has agreed to; a passing suite would then assert the
   wrong thing.

Hence: no endpoint here calls a provider, `RapidoAdapter`, `UberAdapter` and
`OlaAdapter` raise `ProviderNotConfiguredError`, and no credential placeholder is
presented as working.

## 13. Future integration requirements

For each provider, in order:

1. **Authorised access.** A signed agreement and documented API (Uber's partner
   API; Ola's partner/affiliate programme, including its mandatory `utm_source`
   token; Rapido's commercial API, if one is offered — no verified public quoting
   API is known today, so Rapido stays `not_configured` until an authorised route
   exists).
2. **Verified capabilities.** Replace `None` with measured facts: the tiers it
   returns, whether coordinates are mandatory, whether quotes expire and for how
   long. Only verified values.
3. **Credentials via environment.** Add the already-declared variables to the
   deployment secret store; nothing in code or fixtures.
4. **One adapter, one file.** Implement `compare()` against the protocol. A shared
   HTTP base class may be added alongside the first real adapter without changing
   the contract. Transport errors stay inside the adapter; a tier the provider
   does not serve returns `UNSUPPORTED`.
5. **No new coupling.** The route, `FareComparisonResponse` and the demo path stay
   untouched. Response ordering, timeouts, isolation and `providerStates` come
   free.
6. **Tests without credentials.** Fakes for the aggregator, recorded-and-sanitised
   fixtures for the adapter's own mapping, and a test that a missing credential
   still yields `not_configured`.
7. **Flip the default only when proven.** `PROVIDER_MODE=live` remains opt-in
   until a live end-to-end run is validated against the app.

Per-provider notes: Uber has a documented HTTPS deep-link format used by the app
today (client-side, no fare data); Ola must never have its `utm_source` fabricated
and currently opens the public booking page; Rapido has no verified third-party
ride-link format and opens its public site. None of those links are a quoting
integration, and none produce a fare.

## 14. Consequences, limitations and trade-offs

**Gains**

- Adding a provider is one adapter plus one `ProviderSpec`; the endpoint, schema
  and app do not change.
- Demo behaviour is preserved exactly, proven twice: the TypeScript parity fixture
  and a byte-for-byte demo response.
- One provider's failure is structurally unable to remove another's quote, and
  every comparison states its provenance.
- The domain layer is testable without FastAPI, Pydantic or credentials.

**Accepted costs and gaps**

- **Live mode is unproven.** No adapter has ever made a network call, so timeouts,
  isolation and capability planning are exercised only by tests with fakes. Real
  behaviour — retry semantics, rate limits, auth refresh, provider-side error
  shapes — is unknown until an integration exists.
- **Capabilities are static declarations.** Nothing checks them against what a
  provider's response actually contains; that check belongs in the first real
  adapter.
- **No retries, caching, circuit breaker, rate limiting or per-provider
  backoff.** Each request fans out once. A provider failing fast costs one call
  per user request, every time.
- **No observability** (§11): no logs, metrics or traces, so production provider
  behaviour is currently unmeasurable.
- **No persistence or history.** Nothing is stored; `providerStates` is per
  response only.
- **No authentication on this API.** It is a local development service; exposing
  it publicly is not supported.
- **No per-quote provenance,** so demo and live quotes cannot be merged into one
  ranking — `MixedQuoteSourcesError` refuses rather than degrades.
- **Capability duplication:** `credentials_required` and the registry's
  `missing_credentials` both describe the same dependency, in different terms
  (fact vs. variable names). They must be kept consistent by hand.
- **The demo generator exists twice** (TypeScript and Python). The parity fixture
  keeps them aligned; it does not remove the duplication.
- **One extra request-scoped object:** the aggregator is rebuilt per request. It
  is stateless and cheap, but it is not a singleton.
- **`latency_ms` measures our call, not provider-side time.** It is wall-clock
  time around the adapter invocation, including event-loop scheduling, so it is a
  diagnostic hint rather than a provider-latency metric.
